# 06 — Стратегия синхронизации

Клиент хранит заметки локально и работает офлайн.
Сервер — источник истины для синхронизированных данных.

---

## Модель

~~~
┌─────────────────┐         HTTP / JSON          ┌─────────────────┐
│  Android-клиент │ ◄──────────────────────────► │  Сервер (API)   │
│                 │                              │                 │
│  Локальная БД   │                              │  PostgreSQL     │
│                 │                              │                 │
│  Очередь        │                              │                 │
│  изменений      │                              │                 │
└─────────────────┘                              └─────────────────┘
~~~

- Клиент читает и пишет заметки **в локальную БД**.
- При появлении интернета запускается синхронизация.
- Сервер не пушит изменения сам — клиент всегда **инициирует** синхронизацию.

---

## Алгоритм синхронизации

Синхронизация состоит из двух фаз. Порядок важен:
сначала тянем с сервера, потом отправляем локальные изменения.

### Фаза 1. Получить изменения с сервера

Клиент хранит метку времени последней синхронизации: `lastSyncAt`.

1. Отправить запрос:

   ~~~
   GET /api/notes?since=<lastSyncAt>
   ~~~

2. Для каждой заметки в ответе:
   - Если заметки с таким `id` нет локально — **вставить**.
   - Если есть и `version` с сервера **больше** локальной — **обновить**.
   - Если есть и `version` с сервера **равен** локальной — **пропустить**.

3. Аналогично запросить удалённые:

   ~~~
   GET /api/notes/deleted?since=<lastSyncAt>
   ~~~

   Для каждой заметки в ответе — удалить из локальной БД
   (или пометить как удалённую).

4. Обновить `lastSyncAt` на текущее время (до этого проверить время, на телефон может быть неточное).

### Фаза 2. Отправить локальные изменения на сервер

Клиент хранит очередь несохранённых изменений.
Для каждого изменения из очереди:

| Локальное действие | Запрос к серверу |
|--------------------|-----------------|
| Создана новая заметка | `POST /api/notes` |
| Отредактирована заметка | `PUT /api/notes/{id}` |
| Удалена заметка | `DELETE /api/notes/{id}` |

После успешного запроса — убрать изменение из очереди
и обновить локальную запись (сохранить новый `id` / `version`).

500, 503, Timeout -> Оставить в очереди, повторить.
401 -> Разобраться с токеном
404 (при PUT/DELETE) -> Удалить из очереди и из локальной БД.
400, 409 -> Удалить из очереди, показать ошибку пользователю (или разрешить конфликт, как описано для 409).

## Разрешение конфликтов

Конфликт возникает, когда клиент отправляет `PUT /api/notes/{id}`,
а на сервере `version` уже отличается от той, что клиент отправил.
Сервер возвращает **`409 Conflict`**.

**Алгоритм для клиента:**

1. Получить `409`.
2. Запросить актуальную версию: `GET /api/notes/{id}`.
3. Перезаписать локальную заметку серверной.
4. Если пользователь хочет продолжить редактирование —
   отредактировать заново на основе актуальной версии.

> Для учебного проекта достаточно стратегии
> **серверная версия побеждает** (server wins).

## Офлайн-работа

| Действие пользователя | Что делает клиент |
|-----------------------|-------------------|
| Создал заметку без интернета | Сохраняет в локальную БД с временным `id` (например локальный UUID). Добавляет в очередь изменений как «создание» |
| Отредактировал заметку без интернета | Обновляет локальную БД. Добавляет в очередь как «обновление». Если заметка ещё не была на сервере — как «создание» |
| Удалил заметку без интернета | Помечает локально как удалённую. Добавляет в очередь как «удаление» |
| Интернет появился | Запускает синхронизацию (Фаза 1 → Фаза 2) |

> **Временный локальный `id`:** пока заметка не отправлена на сервер,
> у неё нет серверного `id`. Клиент генерирует локальный UUID
> и использует его внутри локальной БД. После успешного `POST /api/notes`
> клиент получает настоящий `id` с сервера и заменяет локальный.

---

## Когда запускать синхронизацию

- При открытии приложения.
- При появлении интернета.
- По кнопке «Обновить» в UI (если есть).
- Периодически по таймеру (опционально, например каждые 15 минут).

---

## Чего клиент НЕ должен делать

- Отправлять несколько `POST /api/auth/refresh` одновременно.
- Отправлять изменения на сервер, если нет интернета.
- Использовать `POST /api/notes` для обновления уже существующей заметки.
  Для обновления — только `PUT`.
- Игнорировать `409`. Если получил конфликт — обязательно
  запросить актуальную версию.
